## 常见坑（都踩过）

- **RDKit 规范 SMILES 不稳定**：要往返校验，见 `stable_smiles`。不同 RDKit 版本可能给出不同的字符串，所以和仓库数据对比时用同一个版本（2026.9.1）。
- **dative Li⁺ 的幽灵自由基**：见 04。
- **多进程**：`fork` 共享全局集合（`network_gen.py`、`lod_build.py`）在 Windows 上不可用；`ec_space` 已经自动切换成 spawn。
- **`pkill -f` 会误杀自己的 shell**：结束后台进程时按 PID 杀。
- **大文件**：GitHub 单个文件 100 MB 上限，用 `split_table.py` 拆；发给用户的文件拆成 ≤ 45 MB 的独立 zip。
- **全量布局**：千倍规模差异时要用立方根缩放，并给 padding 设上限，否则小列宽度会变成负数。
- **zip 里的中文文件名**：Linux 的 `zip -r`（Info-ZIP 3.0）按 UTF-8 存文件名，但不设 UTF-8 标志位（bit 11）。Windows 自带解压会按 GBK 读，显示乱码或报"压缩文件夹无效 / 损坏"（2026-11-05 用户反馈推荐版离线 zip "一直显示损坏"）。含中文文件名的 zip 一律用 Python `zipfile` 打包，它会设 0x800 标志；可以用 `ZipInfo.flag_bits & 0x800` 检查。
- **分卷**：Info-ZIP 的 `zip -s 45m` 分卷，合并后 `unzip` 报"invalid compressed data / overlapped components"，不要用。可靠的做法是先做单个 zip 并验证，再 `split -b 45M -d --numeric-suffixes=1` 切成 `.zip.001…`：7-Zip / Bandizip 能直接打开，`copy /b` 或 `cat` 能拼回原文件，用 SHA-256 校验。
